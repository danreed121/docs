This section documents all operations in the REST API for LCMR Writes. These operations share commonality in parameters, functionality, and return data.

## Operations

| Operation | Description | Page |
|-----------|-------------|------|
| [Load](/api/operations/load) | Store new content or update existing content | PATCH / POST |
| [Set Properties](/api/operations/set-properties) | Update properties on existing content | PATCH |
| [Delete](/api/operations/delete) | Soft-delete a Content Instance | PATCH |
| [Restore](/api/operations/restore) | Restore a deleted Content Instance | PATCH |
| [Pass](/api/operations/pass) | Pass content through a transform without writing | PATCH / POST |

## HTTP Methods

PATCH is used for most operations rather than PUT, because these operations pass only the properties to be changed — unmentioned properties are carried over from the last Content Instance. This partial-update semantic aligns with PATCH, not PUT (which requires specifying the entire resource and must be idempotent).

For consistency, PATCH is also used for DELETE and RESTORE even though other HTTP methods could technically apply. Operations are distinguished by the final path segment rather than by HTTP method.

**POST** is used in two cases:

- **Load** — When storing new content where the `XmsContentId` will be generated by the system, or for updates where content identification is handled by extraction (e.g., XML content containing the identifying property).
- **Pass** — When the XSLT entirely contains the logic to determine the content to be operated on.

**PATCH** always includes the `XmsContentId` (and optionally Tag) in the path, identifying the *destination* content to be affected. **POST** does not include `XmsContentId` in the path, as that will be identified later.

<Tip>
Path parameters identify the *destination* content, not the *source* content. Source content is specified by form parameters (`srcContentId`, `srcFile`).
</Tip>
